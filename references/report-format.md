# 巡检报告阅读与排版规范

用户明确偏好结构清楚的报告和指标表格。QQ 输出保留 Markdown 标题、重点加粗和表格；用完整句子组织内容，让用户容易找到“结论、证据、下一步”。不要再退化成无层级的纯文本短行。

## 阅读顺序

1. **报告开头**：一个报告标题；总体状态与告警数量；扫描时间（含时区）与主机；一句概括已检查资源/服务状态和优先事项的结论。状态用中文，Healthy 对应“正常”、Warning 对应“需要关注”、Critical 对应“严重异常”。仅总体状态使用一个状态图标，正文不堆图标。
2. **重点关注**：仅有告警时显示。Critical 优先，其余按实际处理优先级排列。每项用一个加粗短标题，随后用“发现”“判断”“建议”等明确标签组织两到三条完整说明。判断仅在解释影响或不确定性确有必要时添加，不套空话。相同根因可合并解释，告警总数仍以 `summary` 为准。
3. **资源与服务**：始终显示三列 Markdown 表格。异常在表中可再次标状态，但不重复长篇解释。
4. **其他观察**：只放未在前面解释的网络访问面线索、日志概览、重要覆盖限制；按主题使用短列表。没有内容就省略，不强制凑满章节。

报告在最后一项实际内容后结束，不输出独立的「检查范围」章节或末尾固定范围说明。确有采集缺失或限制影响结论时，在对应异常、指标或观察旁简短注明。

## 视觉与文字

- 报告标题用一级标题，各区用二级标题，具体问题用加粗短标题；不要同时混用【方括号标题】、罗马数字、多层编号或大片分隔线。
- 标题、段落、列表和表格之间留一空行；每个问题单独成块。句子按语义写完，由客户端自动折行，不按“35字一行”等长度强行拆句。不逐词加粗，也不整段加粗。
- 加粗用于总体结论、问题名称、关键异常数值或建议标签，让视线有落点。数据、状态和行动分清层次，避免把所有内容压成一串斜杠或箭头。
- 正常读数简洁呈现，异常保留足够的原因、证据和下一步。不要为了压缩字数丢掉可用容量、日志类型、关键时间或异常影响；也不要为显得完整每日复述所有技术细节。
- 一个普通告警报告通常可用约600–1000汉字说明清楚，正常报告可更短；这只是尺度参考，不硬截断，也不为凑字数添加内容。
- 使用用户能理解的词：例如“僵尸进程”首次出现时解释为“已退出但未被父进程回收的进程”。使用标准术语辅助定位即可，不堆满 PID、单元全名、命名空间或 schema 等词。

## 资源与服务表格

固定列名：`项目 | 当前值 | 状态`。表头和分隔行完整，前后各空一行；不包代码围栏，不手动换行单元格，不用空格模拟列。即使在 QQ 中也保留用户指定的表格。

- 至少包括 CPU、内存、根分区、1分钟每核负载、Inode、Swap、Gateway、失败服务。其他异常挂载可增加行，不用枚举每个 overlay；不要把最高使用率与根分区值混为一谈。
- 单元格保持短，状态按实际值及 `thresholds` 判断。正常项写“正常”；达到阈值写“告警”或“严重”；无数据写“未获取/未确认”；不适用项目写“不适用”。
- 内存及根分区可用空间放在表后独立的“可用余量”一句中，保留单位；Inode最高值、EFI不适用等口径放在紧接的简短注释中。避免长说明撑宽表格。
- 无 Swap 写“未配置”，不写0%；`inode_applicable: false` 才是不适用，其他缺失属于覆盖限制。
- Gateway 的当前值可写实际的 active/running，状态写“运行中”；仅确认系统服务状态不能推断业务健康。系统和用户级失败服务分别给数量，采集失败不能填0。
- 正常行不重复整套阈值；异常的当前值和触发阈值在对应关注项中解释。表格后不再重复一遍表内全部数据。

## 证据与行动

- 每项发现给具体数值、时间窗或观察，并用一步可执行的排查建议收束。把“观察到什么”与“可能意味着什么”分开，避免只列数字或笼统说“注意安全”。建议不是已执行的操作，不自动修复。
- 日志按来源和错误类型聚类，保留确实帮助判断的数量或集中时段。计数是优先级0–3的日志记录，不等于失败登录次数或全部登录事件。重复认证失败可以提示疑似探测，但不能断言已入侵或有成功登录。
- `count_is_lower_bound: true` 时写“至少”；`sample_by_unit`/`sample_by_priority` 只代表保留样本；截断、无权限、跳过或命令失败需明确。已在关注项说明的日志，不在“其他观察”重述。
- 非回环监听按实际用途解释，挑几个值得核对的端口即可；绑定地址不能证明公网可达，也不能把组播或指定接口绑定一律当风险。没有做 DNS/ICMP/外部测试时不宣称通过。
- 用 `coverage.limitations` 和采集器状态检查漏项。degraded 可伴非零退出码；unknown、超时和空数组不能证明服务正常或故障。旧 schema 缺字段时说明限制，不补造数据。
- 本机、容器或宿主机视野按已证实的环境描述；单次负载快照不证明持续故障。只在相关结论确受影响时简注具体限制，不罗列未执行检查清单。
- 对来源地址、账号、PID、单元全名选择性披露，仅在定位必要或用户要求详情时列出；密钥、令牌、完整日志继续脱敏。不把本机文件路径、任务ID、schema版本或工具过程塞进用户报告。

## 版式示例

以下是示意，不是本次事实。时间、主机、数值、状态、发现与建议须来自本次扫描。示例代码围栏仅用于隔开文档内容，实际报告不要输出围栏。

```markdown
# 服务器巡检报告

**总体状态：🟠 需要关注** · 2 项告警，0 项严重异常

- **扫描时间：** 2026-11-13 23:12（北京时间）
- **主机：** example-server

**结论：** 资源使用有余量，Gateway 服务运行中；优先核查 SSH 异常认证，并观察僵尸进程是否增加。

## 重点关注

**1. SSH 异常认证｜优先核查**

- **发现：** 最近24小时有 **27条错误日志**，超过20条告警阈值，主要是同一来源反复尝试多个账号。
- **判断：** 这些认证失败记录提示可能存在自动化探测，但不足以证明已成功登录或入侵。
- **建议：** 核对对应时段的成功登录记录，并检查 SSH 的来源访问限制。

**2. 1个僵尸进程｜观察是否增加**

- **发现：** codex 已退出但未被父进程回收，数量达到1个的告警阈值。
- **建议：** 检查父进程的回收情况并观察数量；单个进程通常影响有限，若持续积累再进一步处理。

## 资源与服务

| 项目 | 当前值 | 状态 |
| --- | --- | --- |
| CPU | 19.3% | 正常 |
| 内存 | 30.8% | 正常 |
| 根分区 | 36% | 正常 |
| 每核负载（1分钟） | 0.09 | 正常 |
| Inode | 最高5% | 正常 |
| Swap | 未配置 | 不适用 |
| Gateway | active/running | 运行中 |
| 失败服务 | 系统0个，用户0个 | 正常 |

**可用余量：** 内存16.2 GiB，根分区124.1 GiB。EFI相关挂载不适用Inode指标。

## 其他观察

- **监听范围：** RPC（111）、打印服务（631）存在全地址监听，建议核对是否需要及其访问限制；尚未验证公网可达性。

```

发送前检查：先看开头能否知道整体状态和优先事项，再看表格能否横向比较各项，最后核对每条异常是否有证据及具体建议。避免相邻多行只是同一句被截断，也避免整段无重点的文字墙。定时任务已经负责投递时直接输出报告，不另发消息。
